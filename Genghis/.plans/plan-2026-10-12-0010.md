# Plan: Faster `<cdrop` Release (bomb-bay readiness at DWID arm) + `<creserve` hold-back guard
*Created: 2026-10-12 00:10* (follows plan-2026-10-11-2333.md)

## Context
Test mission with Blenheim cover bombers produced two problems:
1. Bombers dropped ~20s+ after the player released his first bomb.
2. Two groups were DWID and two were RESERVED, but all four dropped (the RESERVED pair should
   have been held back).

Both live in `Genghis-Class-CoverMission.cs`.

### Root cause 1 (late drop)
`coverDropReleasePass()` applies its MAIN gate lazily — the bomb-bay-door wait (Step C8) only
starts inside the release pass, i.e. the moment the leader drops and the watcher walks the
groups. A group whose `A_BombBayDoor < 0.98` is `HELD` (throttled `cdDropPassLog("HELD: ...")`,
`continue`) and re-polled every 750ms; `coverDropBayWaitFallback_s = 30` is the only timeout.
Aircraft that have no operable bomb-bay door (Blenheim, Ju-87, most fighters, Sturmovik) never
read open, so they sit HELD until the 30s fallback — hence the 20s+ delay.

### Root cause 2 (RESERVED dropped)
`<creserve` sets `coverAircraftAirGroupsOrders[airGroup] == CoverAGOrders.reserve`.
`dropBombsNow_player()` (Step D) skips those groups, and `coverDropReleasePass()` does NOT.
Since the `CoverAGOrders.drop` machinery was removed, nothing in the automatic release pass
currently consults the reserve order — so a RESERVED group can be released on the leader's drop.

## Accepted design
Start the door-readiness window when DWID mode is DECLARED (`BAM_enterDropMode`), not when the
player drops. Classify each group's doors once at arm time so that the release after the leader
drops is fast regardless of when his bomb left the bay. Add an explicit reserve guard to the
automatic release pass.

## Plan

### Fix 1a (readiness declared at DWID arm)  [COMPLETED-2026-10-12-0018]
- Add two new per-group state dicts (same life cycle as `coverAircraftAirGroupsBayWaitSince`,
  i.e. cleared on re-arm in `armCoverDropWatch` and by `forgetAirGroup`):
  - `ConcurrentDictionary<AiAirGroup, bool> coverAircraftAirGroupsDoorsNeverOpen` — true if, at
    arm time, `A_BombBayDoor < coverDropBayOpenThreshold` (a clean 0 / -1 / no door parameter).
  - `ConcurrentDictionary<AiAirGroup, bool> coverAircraftAirGroupsDoorsInitiallyOpen` — true if
    the door was already open (>= 0.98) at arm time.
- In `BAM_enterDropMode()`, right after `armCoverDropWatch(player)`:
  for each active airgroup owned by this player, probe `coverDropBayDoorPos(airGroup)` once and
  populate the two dicts. (No per-group wait here — we only CLASSIFY; waiting still happens in
  the release pass for slow-but-real doors.)
  - **CLARIFIED + implemented:** `doorsNeverOpen` = `bayPos < 0` (the -1 "no door" signal only),
    per the user's approved Option 1. A real-but-shut door reads 0 → classified as NEITHER, so it
    keeps the lazy wait (protects the one-salvo latch). Done via new helper `cdProbeBayDoorsAtArm(player)`,
    called from `BAM_enterDropMode()` right after `armCoverDropWatch(player)`; both dicts also cleared
    in `armCoverDropWatch()` and `forgetAirGroup()`.

### Fix 1b (gate rewrite in `coverDropReleasePass()`)  [COMPLETED-2026-10-12-0018]
- Replace the current lazy `HELD` block with a combined decision using the two new dicts:
  - If `doorsNeverOpen[airGroup]`  → skip the door-wait entirely; release on the next safe gate.
  - Else if `doorsInitiallyOpen[airGroup]` → release normally (no wait).
  - Else (real door, not yet open at arm) → keep the existing door-wait with the 30s
    `coverDropBayWaitFallback_s` fallback.
- Keep `cdDropPreOpenBays = true` (pre-open attack waypoint keeps real doors open).
- Result: 30s ceiling stays for slow-but-real doors; the ~20s wait disappears for doorless types.
  - **Implemented:** `doorsOpen = (bayPos >= threshold) || doorsNeverOpen || doorsInitiallyOpen`.
    `doorsOpen` stays in scope for the BAY LEAD-IN calc below (`lead_m = doorsOpen ? 0 : ...`), so a
    doorless group gets `lead_m = 0` (no door cycle to lead into).

### Fix 2 (RESERVED hold-back guard in the automatic pass)  [COMPLETED-2026-10-12-0018]
- Add `if (orders == CoverAGOrders.reserve) continue;` in `coverDropReleasePass()` (in addition
  to the existing skip in `dropBombsNow_player()`), where `orders` is read from
  `coverAircraftAirGroupsOrders[airGroup]` (default `normal` when absent).
- Log `HELD: orders=reserve` immediately via `cdDropPassLog(airGroup, "HELD: orders=reserve", always: true)`
  so the test server shows WHY a group was held.
  - **Implemented:** guard added right after the torpedoes skip, alongside the other skip conditions,
    using `coverAircraftAirGroupsOrders.ContainsKey(airGroup) && [...] == CoverAGOrders.reserve`,
    logged with `always: true` (no 5s throttle).

### Fix 3 (walk-forward safety net — verify only)  [VERIFIED-2026-10-12-0018]
- Confirm the ahead-of-line gate (`pastLine_m` vs `coverDropMaxAheadWait_m` = 3000m, plus the
  separate `coverDropMaxAhead_m` bound) bounds the walk-forward delay, and that a group released
  into the 25s `coverDropHoldFlightPlan_s` hold-off is never re-counted as issued (it is not —
  `coverAircraftAirGroupsDroppedThisPass` guards it). No edit expected unless a gap is found.
  - **Verified, no gap:** ahead-gate `maxAhead_m = everWaited ? 3000m : 1000m` skips too-far-ahead
    groups WITHOUT setting `anyStillArmed` (watcher stands down); `coverAircraftAirGroupsDroppedThisPass`
    latches a released group and (by design) does NOT set `issuedAnyThisPass`, so it is never
    re-counted. No edit made.
