## Root cause — confirmed by the week-42 log

The ACT-mode implementation classified a "doorless" bomber as `neverOpen = (bayPos < 0)`
(Genghis-Class-CoverMission.cs:934), i.e. it assumed aircraft without a usable bay door read `-1`.
The week-42 log proves that assumption is wrong for the aircraft actually being flown:

1. **Every Blenheim reads `bay=0.000`, not `-1`, at DWID arm.** All 19 arm-time probes in the
   session (`<cdrop ARM: …bay-doors bay=0.000 -> neverOpen=False initiallyOpen=False`,
   04:17:37 / 04:20:31 / 04:20:41 / 04:24:05) return `0.000`. So `neverOpen` is ALWAYS False for
   them -> they are classified as *neither* and fall into the lazy door-wait branch
   (`:2810` `if (!doorsOpen)`).

2. **The wait clock starts lazily, on the player's drop — not at arm.**
   `coverAircraftAirGroupsBayWaitSince` is first stamped inside `coverDropReleasePass` (`:2812`)
   the moment the pass runs after the drop (first `HELD` at 04:21:49), even though DWID was armed
   at 04:20:41. So the 30 s runs AFTER the drop, exactly as observed.

3. **The Blenheim door can never satisfy the gate before release — a structural deadlock.**
   The door "opens automatically when a bomb is released … as though on springs".  Confirmed by the
   DROPTRACE data: the only non-zero `bay=` values in the whole file (`0.600`, `0.900`, `1.000`)
   appear at the +1s/+3s ladder points AFTER a release was issued — e.g. 04:22:20, one second after
   the 30 s fallback fired at 04:22:19.  Before release it is pinned at `0.000` for the entire wait
   -> `"…bomb-bay doors never opened (bay=0.000) after 30s - releasing anyway"`.  Waiting for a
   spring door to pre-open can never succeed; only the 30 s fallback breaks the deadlock.  That is
   the 20-30 s lag, on both drops.

So the original design intent is exactly right — **the wait clock must start when DWID mode is
declared, so the 30 s budget is spent during the run-in, not after the drop.**  The `-1` heuristic
was the wrong mechanism to get there.

### Why a SEPARATE `ArmedAt` dict rather than seeding `BayWaitSince` at arm
Seeding `BayWaitSince` at arm would flip `everWaited` true for every group the instant DWID is
armed, which widens the ahead-of-drop-line skip limit from `coverDropMaxAhead_m` (1000 m) to
`coverDropMaxAheadWait_m` (3000 m) — an unintended loosening of the walk-forward safety bound
(verified in plan-2026-10-12-0010 Fix 3).  A dedicated `ArmedAt` used ONLY for the fallback
deadline changes exactly one thing (when the 30 s starts) and leaves the ahead-gate byte-for-byte
identical.

### Optional hardening (opt-in — INCLUDED per user request)  [COMPLETED-2026-10-12-1102]
Because a spring-door type's `bay=` stays pinned at exactly `0.000` for the whole run-in while a
real-door type transiently shows `0.6-0.9` as it cycles, we COULD add: once a group has been armed
> ~8-10 s with `bay` still exactly `0.000`, treat it as "won't pre-open" and release on the next
pass immediately (no 30 s).  This makes even sub-30 s drops fast and needs no type list.  It adds a
new heuristic and a little risk, so it is offered as an opt-in.  Default: Steps 1-3 only
("clock starts at arm").
