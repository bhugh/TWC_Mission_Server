            {
                // Throttle: if another upload just happened, wait before this one.
                if (stb_SftpLastUpload != DateTime.MinValue)
                {
                    TimeSpan sinceLast = DateTime.Now - stb_SftpLastUpload;
                    if (sinceLast < stb_SftpMinDelayBetweenUploads)

                        int sleepMs = (int)(stb_SftpMinDelayBetweenUploads.TotalMilliseconds - sinceLast.TotalMilliseconds);
                        if (sleepMs > 0)
                        {
                            Thread.Sleep(sleepMs);
                        }
                    }

                stb_SftpLastUpload = DateTime.Now;

                // Backoff: if connect/login recently failed, do not retry yet.
                if (DateTime.Now < stb_SftpBackoffUntil)
                {
                    Console.WriteLine("SFTP UPLOAD: skipped - in backoff cooldown {0}", filename);

                    stb_SftpConnected = true;

                {

                    if ((DateTime.Now - stb_SftpLastConnectAttempt).TotalSeconds < stb_SftpConnectBackoff.TotalSeconds)

                    if (stb_SftpClient != null)

Key behavior of the new implementation:
1. **Connection reuse:** Once `SftpClient.Connect()` succeeds, the same instance is kept in `stb_SftpClient` and reused on every subsequent call. No new TCP/SSH handshake per file.
2. **Inter-upload delay:** Before each upload, if less than `stb_SftpMinDelayBetweenUploads` (5 s) has passed since the last upload, the thread sleeps for the remainder. This paces connections so the remote host doesn't see a burst.
3. **Connect/login backoff:** If `Connect()` or authentication throws, `stb_SftpBackoffUntil` is set to `Now + 30 s`. All calls within that window return `false` immediately without touching the network. After the window expires, the next call retries.
4. **Upload failure backoff:** If `sftp.UploadFile` throws, the client is disposed, `stb_SftpBackoffUntil` is set, and the next call retries after the backoff window.
5. **Stale connection recovery:** If `stb_SftpClient.IsConnected` becomes false (remote dropped it), the code disposes the dead client and opens a fresh one on the next call.
6. The `ftp://` URI in `stats.ini` is still parsed for host/port/path, but the actual transport is SFTP on port 22 (or the URI port).

## Assumptions & limitations (for the worker to note, not to "fix" now)

- **Single process lifetime:** The reused `SftpClient` stays open for the life of the StatsMission instance (typically the whole server run). It is only recreated after a failure. There is no explicit shutdown/disconnect hook — acceptable because the process ends when the server stops.
- **Hardcoded tuning values:** `stb_SftpConnectBackoff` (30 s) and `stb_SftpMinDelayBetweenUploads` (5 s) are constants in code. They can be adjusted here or later moved to `stats.ini` if desired.
- **One connection at a time:** The `lock` serializes uploads across all call sites, so radar/stats/tacview uploads queue up rather than running in parallel. This is intentional to protect the single SFTP session and pace the remote host.
- **Thread safety:** `lock (stb_SftpLock)` guards all reads/writes of the connection fields. `Thread.Sleep` inside the lock blocks only that thread's upload; other callers wait on the lock.
- **C#5 verified:** No `$"..."`, `out var`, `is T x`, `?.`, `nameof`, or `var` appears in the new code.
